# Flowctl Deterministic Control Contract

Every validated external-review manifest must be consumed with `flowctl review cursor --binding-id <binding>` or `flowctl review ibrain --binding-id <binding>`; `--manifest <path>` validates and consumes in one invocation. Include the target artifact and each necessary source, test, or evidence file explicitly. Execution rematerializes and rechecks the exact set, prompt, paths, original source digests, transmitted digests, and authorization revision; it cannot silently substitute a target-only package. Code requires its recorded snapshot, while Spec and Plan bind current Git HEAD/status facts. Ignored, sensitive, symlink, non-regular, outside-worktree, oversized, or drifting inputs fail before transmission. Local artifact location metadata is neutralized in transmitted bytes; original source, body, and approval digests remain bound.

Replay validation and execution require `flow-integration`, the active milestone, a registered approved Requirement and Plan, and manifest `milestone_id`, `scenario_id`, `plan_revision`, and `plan_digest`. The matching Plan scenario must require production-derived data and pin `production_dependency.replay_manifest_digest`: SHA-256 of canonical JSON of the manifest excluding those four binding fields. This pins the commands, limits, destination, retention, sanitizer, and policy without a circular Plan digest. Validation and execution both recheck current Plan approval and digests.

Unresolved replay `BLOCKED_CLEANUP` or `INTERRUPTED` evidence blocks every progression, handoff, resume, and signal entry. An authorization amendment cannot clear it. Use `flowctl replay cleanup --state <state> --binding-id <original-binding> --expected-revision <revision>` to prove the recorded outputs absent in the original private directory. Recovery never runs the adapter cleanup command or deletes the final destination: a pathname ownership check cannot make a later adapter deletion atomic. Recovery can remove only the controller's random staging name after matching execution-time persisted device, inode, and content digest. An existing final destination, missing ownership evidence, changed directory/executable, or an explicit adapter cleanup failure remains blocked. An interrupted run with no outputs can recover without executing cleanup. The controller records `REPLAY_CLEANUP_RECOVERY`; a successful proof is terminal, and repeated calls return that proof without cleanup or another state mutation.

An Integration artifact may omit `integration_results` only when its bound approved Plan is a legacy checkpoint without `integration_scenarios`. New Plan contracts require complete results at registration, handoff, and resume.

`flowctl` is the sole writer of `flow-state.json` and `flow-events.jsonl`, and the sole authority for mechanical Flow progression. Agents and skills must not edit the controller or event log, calculate or trust their own digest as workflow fact, count their own review attempts, classify process failures, choose a resume checkpoint, or declare a handoff accepted.

Resolve the executable in this order: an explicitly supplied `FLOWCTL` path, this package's `flowctl.py`, then `~/.codex/flow-v2/flowctl.py`. Failure to locate or execute it is `FLOW_CONTROLLER_UNAVAILABLE`; do not fall back to prompt-owned state.

Every command emits one structured JSON object. Read its returned `state_revision` before mutation and pass it back as `--expected-revision`; `STATE_CONFLICT` requires reloading with `flowctl status`, never overwriting state. Mutations are serialized by a file lock, journaled for crash recovery, atomically replace controller JSON, and append a SHA-256-linked event; status audits the state revision against that event chain. The controller does not trust caller-supplied digests, approvals, retry counts, failure classes, checkpoint depth, or successful-transition claims.

## Required command boundary

- At entry, run `flowctl status --state <controller>`. This revalidates issue, repository worktree, and branch.
- At initial or interrupted orchestration, run `flowctl resume --issue <issue> --repo <worktree> --state <controller> --expected-revision <n>`; provide `--inputs <json>` for explicit arbitrary-node documents. Use only its verified checkpoint and `pending_action`.
- After writing an artifact, run `flowctl artifact register --state <controller> --path <path> --type <kind> [--milestone <id>] --expected-revision <n>`. The controller recomputes canonical bytes, approval, upstream binding, revision monotonicity, and invalidation.
- For GPT review, run `flowctl review begin ... --backend gpt`, dispatch the bound review, then `flowctl review submit`. GPT judgment is caller-attested, but binding, schema, evidence fields, cycle count, and artifact freshness are controller-checked.
- For Cursor, create a bound prompt and run `flowctl review cursor`. After two retryable Cursor process failures (`RUN_ERROR` or `PROTOCOL_ERROR`), run `flowctl review ibrain` with fixed `glm-5.3`. The controller validates bindings and executes each runner. Terminal reports are framed by `FLOW_REVIEW_REPORT_BEGIN` and `FLOW_REVIEW_REPORT_END`; structured runtime errors are framed by `FLOW_REVIEW_ERROR_BEGIN` and `FLOW_REVIEW_ERROR_END`. An opaque nonzero exit without a valid report is `RUN_ERROR/UNKNOWN_BACKEND_FAILURE`; a normal exit without a valid report is `PROTOCOL_ERROR`. Neither is approval. Conflicting report/error signals remain `UNCLASSIFIED`. Do not invoke either backend separately and later claim it as controlled review.
- Submit only the handoff JSON defined by `schemas/handoff.schema.json` to `flowctl handoff accept`. The schema validates context-independent shape and globally known values; the controller validates the context-dependent transition from current state. Only acceptance changes stages. A rejected handoff returns to the owning stage without advancing.
- `flow-code` records its one session-scoped coder through `flowctl coder update`; this is the only supported writer for coder lifecycle and replacement generation.
- Before Code review and handoff, run `flowctl snapshot capture`; Code-to-Integration handoff is rejected if the current worktree no longer matches that controller-recorded snapshot.
- Record `FLOW_RUN_HUMAN_GATE`, `FLOW_RUN_BLOCKED`, and `FLOW_RUN_ROUTE_BACK` through `flowctl signal record` using `schemas/signal.schema.json`. Route-back invalidation and pause state are controller mutations, never prose-only Agent claims.
- `FLOW_RUN_HUMAN_GATE` and `FLOW_RUN_BLOCKED` pause all progression mechanically. After the named condition is actually satisfied, record `FLOW_RUN_RESUMED` with the same issue, run, and stage binding, then call `flowctl resume`; never clear a pause by editing state or merely asserting that it is resolved.
- Resolve a pending structured decision only through `flowctl authorization decide`. Open a legal decision or scope change through `flowctl authorization amend`, then call `authorization decide` only after the bound human gate confirms the proposed difference. Immediately before external review or production replay, call `flowctl authorization validate` with the exact operation manifest. It returns an authorization reference and single-use binding; it never broadens scope.

Spec, Plan, and Code carry the same active authorization revision for `external_review` until a controller amendment or identity invalidation replaces it. Each review revision, retry, and iBrain fallback requires a fresh single-use operation manifest. Cursor and iBrain bindings are never interchangeable. These operations, and `flowctl resume`, must not re-prompt while the authorization ID/revision and proposed manifest remain inside the admitted issue, run, worktree, stage, backend, paths, and exclusions. A denial remains stable and pauses once before the first required review; recovery uses amendment rather than a later stage gate.

The active `production_replay` authorization reaches Plan and Integration by ID/revision. `SANITIZED_LOCAL_REPLAY` additionally requires a Plan-pinned manifest validated before acquisition; `SKIP_PRODUCTION_REPLAY` is an active decision that authorizes only the documented skip-and-gap behavior. An `external_review` decision persists a non-empty, duplicate-free `allowed_stages` subset of `flow-spec`, `flow-plan`, and `flow-code`. The consolidated run gate records all three; Direct invocation records only its current stage. Idempotence, denial, and amendment compare both the decision and this scope. Scope expansion or change requires amendment, invalidates the prior binding, and must fail manifest validation for any stage outside the persisted set.

Spec, Plan, and Code require an independently converged GPT Lane, then a Cursor Lane. Each reviewer owns its findings and rechecks the resulting revision. Cursor receives one retry for `RUN_ERROR` or `PROTOCOL_ERROR`; after two retryable process failures, iBrain/`glm-5.3` substitutes and receives one retry. Findings, denied transmission, drift, conflicting reports, and conflicting report/error signals are never fallback conditions. Only those genuine ambiguities count toward two `UNCLASSIFIED` attempts and end `BLOCKED_REVIEW`. Unknown vendor wording is never guessed: a controller-observed nonzero process without a valid report is `UNKNOWN_BACKEND_FAILURE`. `flowctl review repair-classification` may reclassify only controller-executed legacy attempts with intact evidence and a recognized old bridge signature; it appends an audit event, never creates PASS, and only reopens retry/fallback. After an external reviewer passes—or both external backends exhaust retryable process failures—a fresh `gpt-6-astra`/`medium` final consistency review must pass on the current digest. Its cycle count is controller-owned and capped at three. Both external backends unavailable may yield only `EXTERNAL_REVIEW_GAP` plus defect completion after consistency passes.

Human product judgment and reviewer content judgment remain semantic inputs. `flowctl` controls whether those inputs are fresh, correctly shaped, correctly bound, ordered, and sufficient to advance; it does not pretend to replace them.

## Host enforcement boundary

This repository cannot force the host Agent to invoke flowctl. If the host omits a required command, the controller cannot advance and later `status` or `resume` exposes detectable non-progression; no prompt or repository script can make tool invocation mandatory inside the host runtime. Flow therefore converts many silent false-progression claims into auditable state mismatches, but host-level mandatory tool routing requires support from the Codex runtime itself.
