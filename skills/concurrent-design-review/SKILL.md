# 并发设计评审

## 概述

双视角评审法：一位从实现细节向上审，一位从系统行为向下审。两者覆盖不同缺陷类型，单独任一都会漏掉对方发现的问题。

本技能是并发、生命周期与共享可变状态设计的**唯一评审派发与覆盖判定入口**。调用方只负责风险识别、提供材料和记录门禁结果；不得预先派发 reviewer、重复指定模型，或以自身检查替代本技能的独立评审。

**甲 = 代码实现派**：验证 Spec 声明的方法/接口是否真实存在，分析锁区间与竞态窗口。
**乙 = 系统健壮派**：枚举极端场景与失败模式，检查公平性、线程边界和生命周期完整性。

## 准入判定

先判断当前 Spec/Plan 的独立评审覆盖情况，再决定是否由当前主 agent 派发子 agent。**“Spec 被修订”本身不再是自动派发复审的条件。**

仅在以下任一条件成立时，当前主 agent 才派发独立双视角评审：

- Spec/Plan 刚创建，尚未完成独立评审；
- 当前不存在覆盖本次设计的外部架构师独立评审。

如果已有外部架构师独立评审，且当前修订仅落实该报告、没有引入新的设计范围，则将外部报告作为本轮独立评审依据，修订完成后直接继续后续工作，不自动派发本技能复审。若修订引入新的设计范围，或外部报告不覆盖当前 Spec/Plan，则按“没有可用外部评审覆盖”处理。

## 独立评审要求

以上准入判定为“需要派发”时，Spec 的作者或当前主 agent 不得自行执行、汇总为“通过”，或以自身检查替代本评审。为避免自审偏差，当前主 agent 必须将完整 Spec、相关代码路径和明确评审范围派发给**独立子 agent**；该子 agent 必须使用 `gpt-5.6-sol`，推理强度为 `high`，并完成甲、乙两个视角。

主 agent 的职责仅限于提供材料、接收评审结论和修订 Spec/Plan。若评审来源是本技能派发的内部子 agent，且修订后需要验证发现，才再次派发独立复审；若评审来源是外部架构师且当前修订仅落实其报告，不得因为修订完成而自动再次派发。主 agent 可以核验评审报告中引用的代码位置，但不得将该核验视为独立评审。

子 agent 的任务说明必须包含：

```
对以下 Spec 进行独立双视角评审。你是独立评审者，不参与 Spec 起草或修订。
按 concurrent-design-review 的甲、乙视角输出全部发现；无发现时也须明确写“无高/中发现”及已核查范围。
仅做只读检查，不修改 Spec、代码或 Plan。
```

## 视角甲：代码实现核查

**定位问题**：Spec 描述的实现与代码库现实不符，或分析停留在假设层面。

### 核查步骤

**1. 方法名 / 接口存在性验证**
- Spec 中每个函数调用名，在代码库中 `grep` 确认存在
- 重点：`self.xxx`、私有方法 `_xxx`、外部导入符号
- 常见陷阱：Spec 用了重构前的旧名，或描述了尚未实现的接口

**2. 真实调用链追踪**
- 从入口函数逐层展开，不依赖 Spec 的流程图假设
- 验证 Spec 声明的"A 调用 B"在真实代码中是否成立
- 例：FC Guard spec v1-v2 写 `self._skill_fc_loop`，实际不存在；真实链是 `run_turn → _rt_run_fc_and_finalize → while → _rt_execute_segment → run_skill_fc_loop`

**3. 锁区间分析（TOCTOU 检查）**
- 画出锁的 acquire/release 时间线
- 在每个 release 点问：释放后到下一个 acquire 前，是否有其他线程可以修改共享状态？
- 危险模式：check（锁内）→ release → act（锁外）
- 安全修法：将 check 和 act 的状态变更合并在同一锁区间内完成

**4. 计数器边界**
- 递增路径是否与递减路径严格一一对应？
- 异常退出路径（return/raise）是否会跳过递减导致永久泄漏？
- 下溢时（计数已为 0 再递减）是否有保护和 ERROR 日志？

**5. 资源释放完整性**
- 每个 enter/acquire 操作，列出所有可能的退出路径（正常、exception、timeout、early return）
- 每条路径末尾是否有对应的 exit/release？

### 输出格式

```
【甲-发现】严重度：高/中/低
位置：Spec 第 N 节 / 伪代码第 N 行
问题：<一句话描述>
根因：<方法不存在 / TOCTOU 窗口 / 泄漏路径>
建议：<具体修改方向>
```

## 视角乙：系统健壮性审查

**定位问题**：实现细节正确，但在极端场景或并发压力下系统行为失控。

### 核查步骤

**1. 饥饿与公平性**
- 高持续负载下，写者/高优先级操作是否永远等不到执行机会？
- 是否有"新请求不断插入，旧请求永久阻塞"的场景？
- 修法：写者等待期间设置标志（如 `_writer_waiting=True`），阻止新请求进入，让现有请求自然排空

**2. asyncio 线程边界**
- 在事件循环线程（async 函数内）调用任何阻塞原语（`threading.Condition.wait`、`time.sleep`、`queue.get(block=True)`）都会冻结该进程所有协程
- 规则：**所有阻塞等待必须 `await asyncio.to_thread(sync_blocking_fn)`**
- 检查点：Spec 中所有 `async def` 函数，列出其内部的同步等待，逐一确认是否在线程池内执行

**3. 生命周期完整性（三层嵌套规则）**
- 计时/追踪上下文（如 `attach_turn_timing`/`detach_turn_timing`）必须在**所有路径**下 detach，包括：
  - 正常返回
  - 中间层 try 捕获异常后 early return
  - 最内层 finally 执行时
- 三层嵌套结构检查：
  ```
  外层 try/finally：保证 detach 在全路径执行
    中层 try/except：捕获 enter 失败，early return（此时内层 finally 不执行 → 不得调用 exit）
    内层 try/finally：保证 exit 与 enter 配对
  ```
- 常见陷阱：把 detach 放在内层 finally → 中层 except early return 时内层 finally 不执行 → 泄漏

**4. 降级策略保守性**
- 超时/失败时的兜底行为，是否比"强制继续"更安全？
- 原则：**宁可跳过一次操作，不可在不确定状态下继续**
- 例：sync 超时 → skip 本次同步（不是强制替换），guard 超时 → 返回兜底文案（不是混用新旧文件）

**5. 极端场景枚举**
主动列出三类场景并验证设计的正确性：
- **零流量**：无活跃 Turn 时，写操作是否立即成功（不死等）？
- **持续满载**：新 Turn 不断进入，写者是否会无限等待？
- **恰好边界**：最后一个 Turn 退出的同时，写者 `wait` 刚好满足条件，是否有竞态？

### 输出格式

```
【乙-发现】严重度：高/中/低
场景：<极端场景描述>
问题：<系统行为描述>
影响：<用户可见的后果>
建议：<修改方向>
```

## 联合评审协议

### 执行顺序

```
0. 先执行“准入判定”：
   → Spec/Plan 刚创建且尚无独立评审，或不存在覆盖当前设计的外部架构师评审：派发独立子 agent（gpt-5.6-sol / high）
   → 已有外部架构师评审且当前修订仅落实其报告：不派发本技能复审，记录并采用外部评审结论

1. 对已派发的内部子 agent 评审，甲先扫：找出 Spec 与代码库现实的偏差
   → 如有偏差，先修正 Spec 再继续（乙在错误基础上审没有意义）

2. 对已派发的内部子 agent 评审，乙后审：基于已验证的实现，穷举失败场景
   → 每个发现标注 严重度（高/中/低）

3. 对已派发的内部子 agent 评审，交叉验证：乙的每个极端场景，甲确认代码路径是否覆盖
   → 防止乙的场景在现有代码中根本无法触发（虚假报警）

4. 独立评审者汇总并分级；主 agent 只接收并落实结论
   → 高：必须在进入 Plan 前修复
   → 中：Plan 中列为实现约束
   → 低：可作为后续优化记录

5. 仅当本技能派发的内部子 agent 评审发现需要修订时，主 agent 才在修订后再次派发独立子 agent 复审；不得由主 agent 宣布通过
   → 外部架构师评审后的修订若仅落实其报告，不自动启动复审
```

### 评审轮次判定

| 条件 | 结论 |
|------|------|
| 外部架构师已完成独立评审，当前修订仅落实其结论 | 不自动启动本技能复审；记录外部评审来源、范围与日期 |
| 内部第 1 轮发现「方法不存在」或「调用链错误」 | 打回重写 Spec，重新开始第 1 轮 |
| 内部第 1 轮发现 TOCTOU 或事件循环阻塞 | 高优修复，进入第 2 轮 |
| 内部第 2 轮发现饥饿或生命周期泄漏 | 高优修复，进入第 3 轮 |
| 内部连续一轮无高/中发现 | 评审通过，记录轮次 + 日期 |

### 评审记录格式

由独立评审结论（外部架构师或子 agent）确认通过后，在 Spec 文件末尾追加：

```
---
**评审状态**：已通过 | 评审轮次：N | 日期：YYYY-MM-DD

**独立评审来源**：外部架构师 / 子 agent
**评审范围**：Spec、Plan 与相关代码路径 | 日期：YYYY-MM-DD

**内部子 agent（仅当来源为子 agent）**：模型：gpt-5.6-sol | 推理：high

**甲视角**（代码实现）：
- 发现 N 项，已修复 N 项（详见 vN 变更说明）

**乙视角**（系统健壮）：
- 发现 N 项，已修复 N 项
- 遗留低优 N 项（已记入 Plan 约束）
```

## 典型缺陷速查

| 缺陷 | 视角 | 检查点 |
|------|------|--------|
| 方法名在代码库不存在 | 甲 | `grep -r "方法名" .` |
| TOCTOU：release 后状态被改 | 甲 | 画锁时间线，找 check→release→act |
| 计数器泄漏（enter 无对应 exit） | 甲 | 列所有退出路径 |
| 写者饥饿（持续负载下永远等不到） | 乙 | 引入 `_writer_waiting` 标志 |
| 事件循环阻塞（async 内 `cond.wait()`） | 乙 | 搜索 async 函数内的同步阻塞 |
| timing context 泄漏（中层 return 跳过内层 finally） | 乙 | 三层嵌套结构 + 每条 return 路径追踪 |
| 降级行为不保守（超时后混用新旧状态） | 乙 | 超时路径 → 必须是 skip 或 safe default |
