# Flowctl Deterministic Control Contract

## Minimum progression boundary

The controller checks only facts necessary for the current next step: issue/worktree/stage identity, readable current output, actual required terminal review receipts, valid retry/fallback thresholds, and execution safety. It records execution and prevents an Agent from declaring unperformed work passed; it does not certify business facts or demand perfect model metadata.

Document serialization, declared digest/revision/upstream/approval tuples, auxiliary review fields, exact explanatory prose, duplicate handoff quality and historical annotations are not hard gates. Compute bookkeeping in code and expose missing history as warnings. Missing current input or unreadable terminal conclusions return to the owning Agent for repair; never convert a controller/bridge defect into business `FLOW_RUN_BLOCKED` or automatically ask the human to unlock it. Unknown conclusions are never PASS.

Use `flowctl audit --state <controller>` or `flowctl artifact verify` only for explicit strict diagnostics. Neither is a prerequisite for normal status, review, handoff, replay or resume. Replay acquisition retains its operation-specific permission, Plan pin, trusted adapter, private destination and cleanup checks.

For every stage's outward status/result/explanation, use the unified stage summary in `orchestration-contract.md`. `status` returns a read-only `stage_summary` for the current controller stage; accepted handoffs return the completed stage's summary. These are derived observations, never extra validation conditions or replacement evidence. Internal approval/review/test statuses keep their existing meaning.

Every validated external-review manifest is consumed with flowctl review cursor --binding-id or flowctl review ibrain --binding-id; --manifest validates and consumes together. Execution rematerializes and rechecks the complete filtered frozen worktree, prompt and digest manifest, not a root-selected file set. Legacy paths are hints only. Backend/stage/artifact/view bindings are single-use and independent of historical human external_review decisions. Read review-contract.md for exclusions, snapshot guards and stdout-only results.

Replay validation and execution require `flow-integration`, the active milestone, a registered approved Requirement and Plan, and manifest `milestone_id`, `scenario_id`, `plan_revision`, and `plan_digest`. The matching Plan scenario must require production-derived data and pin `production_dependency.replay_manifest_digest`: SHA-256 of canonical JSON of the manifest excluding those four binding fields. This pins the commands, limits, destination, retention, sanitizer, and policy without a circular Plan digest. Validation and execution both recheck current Plan approval and digests.

Unresolved replay `BLOCKED_CLEANUP` or `INTERRUPTED` evidence blocks every progression, handoff, resume, and signal entry. An authorization amendment cannot clear it. Use `flowctl replay cleanup --state <state> --binding-id <original-binding> --expected-revision <revision>` to prove the recorded outputs absent in the original private directory. Recovery never runs the adapter cleanup command or deletes the final destination: a pathname ownership check cannot make a later adapter deletion atomic. Recovery can remove only the controller's random staging name after matching execution-time persisted device, inode, and content digest. An existing final destination, missing ownership evidence, changed directory/executable, or an explicit adapter cleanup failure remains blocked. An interrupted run with no outputs can recover without executing cleanup. The controller records `REPLAY_CLEANUP_RECOVERY`; a successful proof is terminal, and repeated calls return that proof without cleanup or another state mutation.

An Integration artifact may omit `integration_results` only when its bound approved Plan is a legacy checkpoint without `integration_scenarios`. New Plan contracts require complete results at registration, handoff, and resume.

`flowctl` is the sole writer of `flow-state.json` and `flow-events.jsonl`, and the sole authority for mechanical Flow progression. Agents and skills must not edit the controller or event log, calculate or trust their own digest as workflow fact, count their own review attempts, classify process failures, choose a resume checkpoint, or declare a handoff accepted.

Resolve the executable in this order: an explicitly supplied `FLOWCTL` path, this package's `flowctl.py`, then `~/.codex/flow-v2/flowctl.py`. Failure to locate or execute it is `FLOW_CONTROLLER_UNAVAILABLE`; do not fall back to prompt-owned state.

Every command emits one structured JSON object. Read its returned `state_revision` before mutation and pass it back as `--expected-revision`; `STATE_CONFLICT` requires reloading with `flowctl status`, never overwriting state. Mutations retain file locking, crash recovery, atomic JSON replacement and linked events. Status reads current facts without auditing every artifact, authorization field or historical event. Actual hashes, receipts and counters are controller-owned; semantic correctness belongs to the Agent and reviewers.

## Required command boundary

### Reviewed-stage lifecycle

Spec, Plan and Code may be registered with approval status `DRAFT` before review. Registration is not approval. Follow the controller's `pending_action`: `snapshot:capture` captures Code evidence; `review:<backend>` (including `:retry`) selects the current lane; `revise:<kind>` requires fixing known blockers. `approve:<kind>` means the required receipts exist but the approval envelope is not complete: update only the APPROVAL region, then register again with the latest state revision. This metadata-only refresh retains receipts bound to unchanged BODY. Only `handoff:<kind>` permits attempting the normal handoff, whose approval and review checks remain enforced.

Resume uses the same next-action selection as review submission and registration, including iBrain fallback and final consistency. It preserves explicitly carried GPT receipts during external-lane repairs and does not restart earlier missing stages for arbitrary-node entry. A historical PASS without its receipt is not approval and can be re-reviewed. An `INCOMPLETE` report with blocking findings requires repair; without blockers it permits a bounded same-content supplementary review, not inferred PASS. Catchable bridge/package failures after an attempt starts are recorded as terminal non-passing attempts before the command returns an error; unresolved ambiguity never authorizes fallback. A host crash or hard kill is not automatically inferred as a completed attempt.

For Code evidence outside `.ai`, its exact registered document path is excluded from the production snapshot so APPROVAL-only updates cannot invalidate the snapshot. Its BODY remains separately digest-bound; other production files remain protected.

- At entry, run `flowctl status --state <controller>`. This revalidates issue, repository worktree, and branch.
- At initial or interrupted orchestration, run `flowctl resume --issue <issue> --repo <worktree> --state <controller> --expected-revision <n>`; provide `--inputs <json>` for arbitrary-node documents. Missing earlier artifacts do not force a restart at Requirement. Discovered Spec/Plan/Code still need actual reviews, not inferred approval from prose.
- After writing an artifact, run `flowctl artifact register --state <controller> --path <path> --type <kind> [--milestone <id>] --expected-revision <n>`. The controller computes actual content identity, increments its own revision and invalidates affected receipts; model-authored bookkeeping is advisory.
- For GPT review, run `flowctl review begin ... --backend gpt`, dispatch the review, then `flowctl review submit`. GPT execution is caller-attested (not host-enforced); a terminal receipt must exist. Reports need an explicit status and a problem summary when failed. Digest binds from the attempt; missing finding IDs, evidence text, severity or recurrence keys are normalized rather than rejected. Extra report fields are ignored. Wrong explicitly supplied digest and contradictory blocking conclusions are not accepted as PASS.
- For Cursor, create a bound prompt and run `flowctl review cursor`. After two retryable Cursor process failures (`RUN_ERROR` or `PROTOCOL_ERROR`), run `flowctl review ibrain` with fixed `glm-5.3`. The controller validates bindings and executes each runner. Terminal reports are framed by `FLOW_REVIEW_REPORT_BEGIN` and `FLOW_REVIEW_REPORT_END`; structured runtime errors are framed by `FLOW_REVIEW_ERROR_BEGIN` and `FLOW_REVIEW_ERROR_END`. An opaque nonzero exit without a valid report is `RUN_ERROR/UNKNOWN_BACKEND_FAILURE`; a normal exit without a valid report is `PROTOCOL_ERROR`. Neither is approval. Conflicting report/error signals remain `UNCLASSIFIED`. Do not invoke either backend separately and later claim it as controlled review.
- Submit only the handoff JSON defined by `schemas/handoff.schema.json` to `flowctl handoff accept`. The schema validates context-independent shape and globally known values; the controller validates the context-dependent transition from current state. Only acceptance changes stages. A rejected handoff returns to the owning stage without advancing.
- `flow-code` records its one session-scoped coder through `flowctl coder update`; this is the only supported writer for coder lifecycle and replacement generation.
- Before Code review and handoff, run `flowctl snapshot capture`; Code-to-Integration handoff is rejected if the current worktree no longer matches that controller-recorded snapshot.
- Record `FLOW_RUN_HUMAN_GATE`, `FLOW_RUN_BLOCKED`, and `FLOW_RUN_ROUTE_BACK` through `flowctl signal record` using `schemas/signal.schema.json`. Route-back invalidation and pause state are controller mutations, never prose-only Agent claims.
- `FLOW_RUN_HUMAN_GATE` and `FLOW_RUN_BLOCKED` pause all progression mechanically. After the named condition is actually satisfied, record `FLOW_RUN_RESUMED` with the same issue, run, and stage binding, then call `flowctl resume`; never clear a pause by editing state or merely asserting that it is resolved.
- Resolve production_replay decisions through flowctl authorization decide/amend and validate replay manifests before acquisition. For external review, the historical authorization validate command validates a package binding only, without a human gate.

Read and enforce [the frozen worktree review contract](review-contract.md). Review the complete filtered frozen worktree with independent exploration; the root brief is not sole evidence. iBrain is organization-trusted; no external-review authorization gate. Reviewer returns stdout/API only and never writes worktree. Freeze by digest (no automatic commit); source/private snapshot verification and single-use package binding are controller-owned.

The active `production_replay` authorization reaches Plan and Integration by ID/revision. `SANITIZED_LOCAL_REPLAY` additionally requires a Plan-pinned manifest validated before acquisition; `SKIP_PRODUCTION_REPLAY` is an active decision that authorizes only the documented skip-and-gap behavior.

Spec, Plan, and Code require an independently converged GPT Lane, then a Cursor Lane. Each reviewer owns its findings and rechecks the resulting revision. Cursor receives one retry for `RUN_ERROR` or `PROTOCOL_ERROR`; after two retryable process failures, iBrain/`glm-5.3` substitutes and receives one retry. Findings, denied transmission, drift, conflicting reports, and conflicting report/error signals are never fallback conditions. Only those genuine ambiguities count toward two `UNCLASSIFIED` attempts and end `BLOCKED_REVIEW`. Unknown vendor wording is never guessed: a controller-observed nonzero process without a valid report is `UNKNOWN_BACKEND_FAILURE`. `flowctl review repair-classification` may reclassify only controller-executed legacy attempts with intact evidence and a recognized old bridge signature; it appends an audit event, never creates PASS, and only reopens retry/fallback. After an external reviewer passes—or both external backends exhaust retryable process failures—a fresh `gpt-6-astra`/`medium` final consistency review must pass on the current digest. Its cycle count is controller-owned and capped at three. Both external backends unavailable may yield only `EXTERNAL_REVIEW_GAP` plus defect completion after consistency passes.

Human product judgment and reviewer content judgment remain semantic inputs. Retry limits are monotone thresholds: two or more eligible retryable failures satisfy exhaustion, never exactly two. A lane's PASS label needs its actual terminal receipt. GPT's independently passed receipt may be explicitly carried through external-lane repairs; final consistency must pass on the current content. No review result or unknown outcome is converted into a runtime-only fallback.

## Host enforcement boundary

This repository cannot force the host Agent to invoke flowctl. If the host omits a required command, the controller cannot advance and later `status` or `resume` exposes detectable non-progression; no prompt or repository script can make tool invocation mandatory inside the host runtime. Flow therefore converts many silent false-progression claims into auditable state mismatches, but host-level mandatory tool routing requires support from the Codex runtime itself.
